# v14：原帧有界提前提交与 Drawable 释放

2026-10-02。基于现有鸣潮 30 秒节奏继续执行真实 Metal/Apple 插帧回放，无需用户重新录制。正式应用保持垂直同步与普通呈现路径；没有关闭正在游玩的鸣潮。

## 本轮修改

- 原帧与中间帧分别学习请求→实际显示的补偿，避免两种提交余量互相改变同一个补偿值。
- 最近 30 个原帧里至少 12 个健康样本后，使用低分位呈现延后值，保留 2 ms 安全边界，最多提前 4 ms 提交原帧；异常长等待不参与学习。
- 提前提交必须等前一个中间帧提交或被放弃。尚未完成时，以异步方式等到原来的提交时刻；不延长原有窗口，不阻塞主线程。原来的序号、epoch、绝对期限、队列容量与看门狗检查保留。
- 获取 Drawable 的专用串行队列设置逐任务 autorelease pool，避免被放弃且未呈现的 Drawable 因继承池延迟释放。
- 图层尺寸、位置和色彩空间只在变化时更新；覆盖层禁用位置、尺寸和显隐的隐式动画。

连续显示顺序为：上一原帧 Z → Z/A 中间帧 → A → A/B 中间帧 → B。A 捕获完成时，Z/A 中间帧才拥有第二个输入，仍要计算。因此 A 转换就绪后的约 16 ms 并非全是冗余；本轮约 12–14 ms 的插帧处理窗口实际参与了前一对帧的顺序安排。只看 A/B 的时间线会遗漏这个依赖。

## 提前提交实际例子

最终回放 sequence=128，按 A 捕获时刻归零：

| 时间 | 事件 |
|---:|---|
| 14.980 ms | 原帧提前提交尝试，前一中间帧尚未提交，暂缓 |
| 15.190 ms | 前一中间帧提交 |
| 15.981 ms | A 提交 |
| 18.175 ms | 原来的提交时刻 |
| 39.916 ms | A 实际显示 |

这个原帧利用了约 2.19 ms 的提交余量，并守住了前一中间帧的顺序。它不是前后两轮同内容的显示收益对比。

## 回放结果与限度

首轮仅稳定布局的控制：输出 79.35 fps，原帧 P50 43.59 ms、P95 49.84 ms，提交年龄 P50 22.33 ms。提前提交回放：同样约 79.35 fps，原帧 P50 43.24 ms、P95 48.56 ms，提交年龄 P50 20.01 ms。两轮零帧序错误，提前路径 508 个复制像素/原 GPU 顺序样本正确。

后续加入逐任务释放边界的最终回放：511 个输入，508 个正确像素与 GPU 顺序样本；463 个原帧使用了非零提前预算，316 次暂缓事件；22 次暂缓检查随后在中间帧已经解决后提前提交。输出 79.75 fps，原帧 P50 43.80 ms、P95 50.08 ms，无自动的 ≥60 ms 呈现停顿、无队列满丢弃、零帧序错误、零日志丢失。

提交提前没有稳定地转化为相等幅度的显示提前，P50 仍在 43–44 ms 波动。现有结果不支持宣布整体延迟大幅下降或稳定达到 2×。窗口系统、正在运行的游戏负载、输入抖动与插帧耗时均影响回放。原帧 GPU 完成→显示仍约 20–23 ms，不能把它当作一段可直接取消的计时器。实际鸣潮 v14 的收益尚未验证。

一轮控制中出现 1066.7 ms 空档：窗口可见未被遮挡，应用未激活，原 GPU 和输入继续，两个获取任务在途，GPU/呈现均无在途。逐任务 autorelease pool 用于明确被丢弃 Drawable 的释放边界；不能仅凭下一轮没有复现就认定一秒等待唯一根因已证实或永不出现。

## 压力与异常验证

45 fps 实际节奏回放叠加处理回调延迟、尺寸切换和人工 1 秒获取阻塞：509 个正确像素/原 GPU 顺序样本，343 个有提前预算的原帧，零帧序错误与日志丢失；人工阻塞与重试造成约 1.87 秒空档，随后恢复，记录器没有将它遮蔽。

最终 30 fps 常规 commandBuffer 路径，叠加同样压力/尺寸/人工阻塞：358 个输入、357 个正确像素样本；32 个原帧得到非零提前预算，5 次暂缓，提前预算不足时使用原提交窗口，零帧序错误和日志丢失。该负载下大部分原帧没有稳定的呈现延后，因此优化自动不启用。

39 项 Swift 测试、7 项 Python 分析器测试通过；脚本检查提前预算上限和中间帧先于提前原帧解决，常规与直接呈现路径均通过像素回读校验。

## 未保留的试验

CAMetalDisplayLink 试验初次错误混用 `present(atTime:)`，触发测试窗口 GameHookFixture [56973] 的 CAMetalDrawableInvalidOperation。改用普通呈现后跑通，但原帧 P50 约 71.06 ms、GPU→显示约 40.72 ms，明显劣化。该试验代码已移除，正式应用和鸣潮没有启用它。

Apple 说明 preferredFrameLatency 是请求值，窗口模式实际延迟可能更大：[官方文档](https://developer.apple.com/documentation/quartzcore/cametaldisplaylink/preferredframelatency)。

强制 CATransaction.flush 试验输出约 65.85 fps，出现 164 次队列满丢弃；没有保留。正式路径继续保持垂直同步；Apple 明确提示关闭同步可能导致撕裂：[官方文档](https://developer.apple.com/documentation/quartzcore/cametallayer/displaysyncenabled)。
