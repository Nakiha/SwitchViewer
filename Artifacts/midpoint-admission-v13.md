# v13：有界中间帧提交余量与时延口径

2026-10-02，基于 10:43:41–10:44:11 的鸣潮实际记录。当前 Release 应用位于 `SwitchViewer.app`，新进程日志标记 `adaptive-v13`。已有鸣潮进程仍加载原库，需要重新通过 SwitchViewer 启动游戏。没有自动关闭用户正在游玩的游戏。

## 45 ms 的来源

v12 主指标对原帧和中间帧参考年龄混合取 P50。中间帧以 A 帧的捕获时刻为参考，自然比 A 原帧晚约半个输入间隔。这轮混合 P50 45.28 ms，原帧 P50 41.68 ms，中间帧参考 P50 56.66 ms。比例变化会使混合 P50 漂移，所以不能把 45 ms 简单解释成一个原帧的阶段总和。

v13 的 `latencyP50/P95` 改为仅原帧捕获→显示；`midpointReferenceAgeP50` 继续独立记录，旧混合口径另存 `allReferenceAgeP50/P95`。这属于口径修正，不是性能收益。输出 FPS 仍包含实际显示的原帧和中间帧。

同一实际原帧 sequence=17180、captureID=8929，按 A 捕获时刻归零：

| 时间 | 事件 |
|---:|---|
| 0 ms | A 开始捕获 |
| 1.244 ms | A 转换就绪 |
| 17.879 ms | A 提交显示 |
| 18.376 ms | A 呈现 GPU 完成 |
| 22.319 ms | B 捕获到达 |
| 41.679 ms | A 实际显示 |

这帧耗时可直接分成捕获/转换 1.244 ms、转换后到提交 16.635 ms、提交到 GPU 完成 0.497 ms、GPU 完成到显示 23.303 ms，恰好总计 41.679 ms。这是单帧相邻事件之差，不是独立 P50 的相加。逐帧原始数据在 `wuwa-v12-latency-timeline.json`。

A 已在 B 到达前 4.440 ms 完成提交；B 到达后 A 再等 19.360 ms 显示。因此捕获、排队、GPU 提交与等待 B 同时进行。原帧不需要等 Apple 算出中间帧。

整轮的原帧 GPU→显示 P50 23.16 ms，包含系统呈现/合成排队和刷新等待。现有事件还不能把这段进一步拆成 WindowServer CPU、合成 GPU、缓冲和扫描阶段，不应全归因于算法处理。

## 修改

以前中间帧截止检查固定要求距下一原帧名义期限超过 submissionLead（约 13–14 ms）。若连续原帧实际显示稳定晚于计划，这个判断会遗漏少量可用时间。

在最近 30 个健康原帧里学习实际显示相对目标的延后，至少 12 个样本后采用低分位值；保留 1 ms 安全余量，最多回收 2 ms、且不超过 lead 的四分之一。提前显示或恢复按时显示后自动撤销余量；≥50 ms 的异常样本不参与学习。该余量只作用于中间帧截止检查。原帧预排策略、帧序、尺寸 epoch、绝对过期、队列容量和看门狗保护保留。

取 Drawable 前后均检查同一个 reserve；丢弃与提交事件新增 `submissionReserve`，可检查执行的实际余量。Fixture 参数 `--strict-midpoint-deadline` 在同一 v13 二进制里恢复原来的截止判断，用于对照。

另一次前后回放：截止丢弃 32→6，显示 79.52→80.62 fps；该次原帧 P50 43.64→45.00 ms，不能忽略系统/算法波动或宣布时延一定下降。两轮一致改善的是截止丢弃与输出交付。当前改动是小幅提高交付率，不保证恒定 2×。

两轮新判断分别有 509 个正确 GPU 顺序与复制像素样本。额外压力回归叠加处理回调延迟、1 秒 Drawable 阻塞及尺寸变化：507 个正确像素、零帧序错误、零日志丢失；记录到 1.84 秒呈现空档（包含人工阻塞和看门狗重试），随后恢复。它验证异常被记录且可恢复，不代表异常被消除。

39 项 Swift 测试和 7 项 Python 分析器测试通过，Release 构建、签名及 diff 检查通过。常规 commandBuffer 呈现路径另行回归，保留与提前捕获路径相同的时延口径。新版本的鸣潮实战收益尚未采集；已有日志足够继续分析，本轮没有要求用户重新录制。
