## 发现的埋点缺陷

两轮 nativePresented/nativeUnconfirmed 均为零，却有 nativeGpuComplete。代码检查发现 `prepareDirect` 在 drawable 已呈现回调内才调用 Swift 捕获入口，随后 v10 再给该 drawable 注册原游戏呈现 handler，错过了本次呈现。另外这个入口传入的是 hook 自己的复制 command buffer，它的 GPU 时间也不应标记成原游戏 GPU 完成时间。

因此 v10 的 nativeGpuComplete 数据不能用于证明原游戏呈现成本，原游戏与插帧层增量也尚未测出。这是测量实现的遗漏，不是游戏没有呈现。

鸣潮捕获开始于原画面呈现回调，面板的“取帧→显示”约 41 ms 是捕获之后的时长；它不包含原游戏先前的渲染及呈现等待。下一步优化应把“GPU 已完成即可开始捕获”与“等待原 drawable 真正呈现后才捕获”区分开。直接在呈现之前复制并不保证 GPU 写入完成，需要正确配对游戏提交和 GPU 同步，不能贸然移走这项保护。

## v11 埋点修正及下一轮

Objective-C 直接呈现入口现在保存请求时刻、已有 presentedTime 与回调时刻，并传给 Swift 同一 captureID；不再重复注册已完成的呈现，也不把复制 buffer 当作游戏 GPU。commandBuffer.present 路径保留正常的 GPU/呈现 handler。新增 captureRoutes 标明两类入口，分析器输出同源 overlayMinusNativeDisplayMs。

此次保持插帧策略，先验证真实额外延迟再决定调度改动。若额外时长确认为约 40 ms，应优先研究提前安全捕获的同步路径，然后才是缩短每对帧预算、修正中间帧截止保护；目前不能声称调度削减 1–2 ms 就能绕过这段前置等待。

直接呈现 fixture 已验证：出现数百个 nativePresented、同源配对完整样本；不存在错误的 nativeGpuToDisplayMs，零帧序错误、零记录丢失。记录见 v11-direct-check.json。模拟结果不代表鸣潮实际延迟。
