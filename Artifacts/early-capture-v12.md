# v12：GPU 完成后捕获与 Drawable 回归

2026-10-02。应用已构建在 `SwitchViewer.app`。

## 修改

之前鸣潮通过 drawable 直接呈现，捕获要等到原游戏图层已经上屏。现在在获取原 drawable 时建立写入记录，跟踪 render attachment、resolve texture 和常用纹理 blit 的命令缓冲；等待已提交写入的 GPU 完成后异步复制，再进行原帧预排和 Apple 插帧。原图层实际显示回调只用于同一帧配对测量，不再阻挡捕获。

未找到已跟踪写入、缓冲尚未提交、写入过多或多队列等情况保留原来的上屏后捕获，并记录降级原因。保留 drawable 至复制完成，防止纹理被池复用；乱序的 GPU 回调不能使较旧原帧重新进入处理。覆盖的是已跟踪的写入方式，不能据此推断任意游戏/Metal API 都能提前捕获。

## 受控回放

相同鸣潮输入节奏、相同 20 ms 原生呈现等待，GPU/Apple 插帧/Metal 呈现实际执行：

| 指标 | 上屏后捕获 | GPU 完成后捕获 |
|---|---:|---:|
| 同一原帧两层显示差 P50 | 41.7 ms | 8.3 ms |
| 实际输出 | 82.6 fps | 84.5 fps |

这不是实际战斗收益。提前捕获测试的 531 帧及 GPU 在途/尺寸变化测试的 536 帧，GPU 顺序与实际复制像素标记均正确，零帧序错误。未提交缓冲的 538 帧全部降级到上屏后捕获。最终压力回归另有 534 个正确像素样本，常规 commandBuffer 路径 537 帧保持原路径。

## 首次实机验证

通过 SwitchViewer 原有“启动鸣潮”进入已有存档，记录加载阶段和场景内两轮。没有操作战斗、任务或库存。

日志：`~/Library/Logs/SwitchViewer/GameInjection/E573C55F-79C8-45C0-8E68-D11FC913EB8F.log`。场景内 traceID=2，1159 次输入全部走提前捕获，无捕获降级；GPU 完成到捕获入口 P50 0.104 ms，P95 0.216 ms。

1116 个配对原帧的“游戏请求原生呈现→插帧层实际显示”P50 49.6 ms，P95 52.0 ms；原层与插帧层显示同一原帧的差 P50 25.0 ms。上一轮 v11 战斗记录分别为 69.2 ms、41.7 ms。场景不同，不能作为同负载 A/B，也不能宣布战斗收益已验证。

Panel 的取帧→显示 P50 为 42.6 ms；捕获起点提前，跨版本不能只看这个数。上面的请求→显示采用固定起点并逐帧配对，不是各阶段 P50 相加；仍不包含输入、游戏逻辑或请求呈现之前的渲染。

## 捕获到的停顿与修复

场景内一次呈现间隔 1066.7 ms，期间原 GPU、原层显示和捕获继续约 40 帧，主线程可见性采样持续，窗口可见且应用活跃；插帧层 nextDrawable 等待 1000.6 ms。这次可明确定位到插帧 Drawable 获取链，而非用健康帧的 P50 掩盖停顿。

队列满时原代码反复隐藏/显示图层，共产生大量 visibility 事件。最终修改：队列满只丢弃该次提交，不切换可见性；先获取调度名额再取消隐藏；赶不上期限的中间帧在获取 Drawable 前拒绝。看门狗对真正无显示/无输入的回退继续保留。该修改减少干扰和无效池占用，但不能保证底层 nextDrawable 永不等待。

注入 1 秒 Drawable 等待并叠加插帧压力的回归仍完整记录停顿与恢复，零帧序错误，队列满没有 visibility 抖动。
