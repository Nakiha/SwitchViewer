# 悬浮工具栏与延迟统计（2026-10-01）

启动 SwitchViewer 默认显示独立、可拖动、不会成为游戏键盘输入目标的悬浮面板。来源按钮打开现有屏幕/采集卡界面，游戏菜单保留鸣潮、其他游戏与测试窗口入口。macOS 26+ 使用 NSGlassEffectView clear 与 NSButton glass；旧系统使用 NSVisualEffectView。右上角菜单栏波形图标切换面板可见性，面板关闭按钮只隐藏工具栏。窗口菜单的“显示悬浮工具栏”也可恢复。隐藏面板不停止插帧或数据收集。

展开后支持最近 60 秒的延迟、帧率、处理耗时曲线。历史最多 120 个窗口统计点；五秒未收到显示数据，当前数值显示为“—”，不会持续展示旧数值。工具栏位置由系统 frame autosave 保存。工具栏属于 SwitchViewer 的窗口，屏幕捕获的 ownWindowNumbers 排除集合包含它。

## 测量定义

此前游戏内模式 ACTIVE 的 processingMs 是 AppleDownsampledFrameInterpolator.submit 到处理回调的耗时，包括代理处理，既不含等待后一帧，也不含最终呈现等待。DISPLAY 是呈现回调计数。

新游戏模式每约一秒输出 METRICS，所有 host time 使用同一单调时钟。结束时使用 MTLDrawable.presentedTime，不使用呈现回调执行时间作为显示时间；实际面板扫描与输入设备不在该软件测量范围。相同微秒呈现时间去重，避免一次刷新内重复计数。

- latencyP50 / latencyP95：前一输入帧取帧时间 → 输出 drawable 呈现时间，原帧与中间帧都以前一帧作为参考。这包含等后一帧、游戏 GPU/复制、RGB→NV12、Apple 处理、调度、显示合成等待。中间帧是双帧合成，不能把该值解释成它唯一真实内容时间戳的延迟。
- 鸣潮直接 drawable 呈现路径要先等原 drawable 呈现后才能安全复制，因此取帧计时不包含游戏此前的输入、逻辑和原画面绘制延迟。它也不是相对原游戏显示的严格净新增延迟。
- processingP50：Apple 处理链路耗时，与之前 processingMs 同口径。
- readyToDisplayP50：Apple 结果就绪 → drawable 呈现，包含调度、获取 drawable、输出编码/GPU、合成呈现等待。
- sourceIntervalP50：被本插帧器接收的输入间隔，可能因 busy 丢弃输入，不能直接称为游戏内部帧率。
- originalAgeP50 / midpointReferenceAgeP50：按原帧、中间帧分组的前帧参考年龄。
- nextDrawableP50 / submitToGPUCompleteP50 / gpuCompleteToDisplayP50：显示分段。GPU 完成使用 command buffer 的 gpuEndTime，避免完成回调派发延迟；GPU 分段在可用时间戳上计算。
- fps：去重后的实际呈现回调密度，不能证明面板扫描帧数。

屏幕/采集卡模式沿用现有 recordDisplayPresentation 分段统计，工具栏按约三秒的窗口展示捕获回调 → 实际呈现的 P50/P95；“处理”在该模式指回调 → 结果就绪，包括等待配对，不等同于 Apple 内部算法耗时。两种来源口径不同，不能直接比较数值。统计窗口内的分段中位数不能直接相加来重建总中位数。

## 本次队列调整

将游戏 overlay 的 maximumDrawableCount 与输出 GPU in-flight 上限从 3 收紧到 2；将预排队容许范围从两个源帧间隔收紧到半个，过时调度重设为当前时间。继续使用一项插帧任务及过时帧丢弃，避免积压。单一 private 取帧纹理在 RGB→NV12 GPU 读取完成后复用，减少每帧大纹理分配；尺寸、像素格式或设备改变时重建。

这些调整约束额外排队和分配，不是严格测量的净延迟改善；未关闭显示同步。真正 mouse-to-photon 需额外的输入时间标记与外部高速摄影/光电测量。双帧插值等待后一帧、代理处理、macOS 合成等待仍是优化方向。

## 菜单栏常驻

应用 bundle 设置 LSUIElement=true，启动阶段使用 accessory activation policy，隐藏 Dock 图标。菜单栏图标左键切换面板，右键/Control 点击提供显示工具栏、画面来源与设置和退出入口。重新打开应用时恢复工具栏。构建脚本也更新已有 bundle 的 LSUIElement，避免仅新建包生效。release 构建及严格签名验证通过，重启后 lsappinfo 确认运行类型为 UIElement。

## 并行原帧与插帧优化（parallel-v2）

移除原帧对 Apple 完成回调的依赖。第二帧复制完成后，先将已经转换好的前帧交给主线程显示，同时进行当前帧转换及 Apple 处理。GameFramePlayoutPlanner 在这一时刻固定原帧、中间帧及下一原帧的时刻；结果就绪后只等待剩余半帧预算，已经晚于下一原帧时刻的中间帧丢弃。递增的呈现序号防止旧中间帧覆盖新原帧，获取 drawable 后再次检查过期时间。

capture busy 仅覆盖复制和 RGB→NV12/提交准备，不再一直持续到 Apple 完成。Apple 的 in-flight 状态单独限制为一项，源帧可以继续捕获、转换和显示；Apple 忙时跳过该帧对的中间帧生成。私有 RGB 纹理只在其转换读取完成后复用，Apple 继续持有独立 NV12 输入。故即使算法赶不上输入帧率，原帧仍无需退化成每隔一帧取一次。

界面增加“原帧”P50。处理曲线统计所有完成的 Apple 任务，包括结果因过期而丢弃的任务，不以成功显示的中间帧筛掉慢任务。没有处理样本时显示“—”，不会把无样本当成 0ms；日志包含 originalSamples、midpointSamples、processingJobs 与 GPU 时间样本数。LOADED 带 pipeline=parallel-v2，便于确认游戏是否加载新版库。

对照方法：保留改动前动态库，使用同一测试程序依次运行旧/新库；都是直接 drawable 呈现、1080p、12 秒测试，60fps 另重复一轮。舍弃前两个统计窗口，以下为余下 9 个窗口各自统计值的中位数，并非原始逐帧样本的全程 P50。并行运行的游戏负载没有锁定，因此不作为严格硬件基准或鸣潮实测。

| 输入 | 原帧参考年龄 P50，旧 → 新 | 输出呈现回调密度，旧 → 新 |
|---|---|---|
| 30fps | 74.69 → 58.02ms | 59.9 → 60.0fps |
| 60fps，第一轮 | 74.65 → 41.34ms | 62.0 → 79.3fps |
| 60fps，第二轮 | 74.46 → 41.34ms | 69.8 → 75.8fps |

60fps 新版输入间隔保持约 16.67ms，旧版多数窗口约 33ms。原帧约减少 33ms；中间帧仍以前帧作参考，约 49.7ms，若用合成中点作为估算内容时间则少半个源帧间隔。未改变界面主要参考年龄的定义来制造延迟下降。

输出帧率受处理中间帧的截止时间限制，60fps 压力较高时部分窗口只保留约 60fps 的原帧，低负载窗口可接近 118fps；不保证稳定 2×。这是优先避免原帧延迟、丢弃过期中间帧的代价。30fps 仍受等第二帧的 33.3ms 和合成呈现等待限制，不能承诺压到 40ms。

最终版本 release 构建及严格签名验证通过，9 个测试通过（新增原帧独立截止时间、晚到输入与重置、非法输入及未来排队重基准测试）。正常 command buffer 呈现和 1080p→720p→1080p 切换 smoke test 通过；界面确认原帧统计正常显示。当前正在运行的鸣潮保留原进程，新库需要下次从工具栏启动游戏时加载。原始日志与汇总位于 latency-parallel-*.log 和 latency-parallel-comparison.json。


## 提前准备原帧（prequeue-v3）

稳定的 30fps 输入不再等后一帧到达才提交前帧。当前帧转成 NV12 后，按最近五个有效源帧间隔的中位数预测呈现时刻；提前至多 20ms 获取 drawable、编码 GPU 绘制并提交，使用 present(_:atTime:) 保留目标呈现时刻。每次预测都锚定该输入帧，不递推累积延迟。首帧/节奏尚未知时沿用等后一帧的路径；尺寸变化和原画面切换清除预测。

30fps 默认呈现目标约为取帧后 1.25 个源帧间隔（41.7ms）。这不是实际显示时间的保证：系统刷新和合成可能将实际显示延后。Apple 结果仍使用该原帧预先固定的中间帧时刻，过期或已有较新原帧提交的结果丢弃，序号以输入帧归属递增。中间帧提交另外预留显示余量，避免明知将跨入下一原帧时段的结果占用显示队列。

负载较高时，按后一帧复制完成、进入工作队列到插帧回调返回的实际时间平滑调整预算（80% 旧值、20% 新值，上限 80ms）；包括当前帧转换和 Apple 提交准备，不能只使用 Apple 报告的算法耗时。对较快输入（预测源间隔小于 25ms），保留 parallel-v2 的第二帧到达后并行显示路径。试验中强行对 60fps 输入提前排队，可能挤掉中间帧或增加原帧显示延迟，因此没有对快输入启用这个策略。

新增日志 originalSubmitAgeP50（原帧从取帧到提交的年龄）、targetErrorP50（实际显示减去目标时刻）、presentationOrderErrors（统计窗口内按呈现时间排序后的序号倒序次数）。原有 latencyP50、originalAgeP50、processingP50 的定义不变。就绪至显示的等待包含主动保留的呈现时段，新旧不能把该分段单独作为优化幅度。主指标仍混合原帧和中间帧、都以前原帧取帧为参考，因此有时顶部依然接近 66ms，而下方原帧已经约 50ms。

对照使用相同 1080p、12 秒直接 drawable 呈现测试窗口，舍弃前两个统计窗口，取剩余 9 个窗口统计值的中位数。不是逐帧样本合并后的全程百分位，也不是鸣潮实测；并行游戏负载、算法波动及系统显示相位没有锁定。

| 原帧输入 | 原帧参考年龄 P50，旧 → 新 | 输出呈现回调密度，旧 → 新 |
|---|---|---|
| 30fps | 66.27 → 49.70ms | 57.6 → 60.0fps |
| 60fps（保留原并行路径） | 41.36 → 41.34ms | 93.5 → 86.4fps |

最终 30fps 原帧提交年龄 P50 约 23.41ms，早于下一输入的 33.33ms；实际目标偏差约 8.03ms。混合参考年龄窗口 P50 的中位数 66.35 → 49.79ms，P95 83.04 → 66.39ms，但单独窗口仍会随原帧/中间帧样本占比变化。60fps 的帧率波动不作为改善结果；两个版本均不保证稳定 2×。较重负载下，提前队列仍可能丢弃过期中间帧，优先保持原帧跟进。

最终 release 构建、严格签名和 14 个自动测试通过。30fps/60fps 直接呈现测试以及正常 command-buffer 呈现的 1080p→720p→1080p 切换均正常退出，无 ERROR，所有最终版本统计窗口的 presentationOrderErrors=0。这检查的是观察到的呈现序号，不等于外部光学验证。

最终日志是 latency-prequeue-release-{30,60,resize}.log，旧库对照为 latency-prequeue-before-{30,60}.log；汇总 latency-prequeue-comparison.json 包含最终库 SHA256。其余 prequeue 日志保留调参过程，不能当作最终版本结果。LOADED pipeline=prequeue-v3 可确认加载新版。应用已重新打包；正在运行的鸣潮未重启，需下次从工具栏启动游戏加载新库。


## 按插帧压力自动调节（adaptive-v4）

以 GameFramePressureController 替换单一耗时平均值。最近 30 项已完成任务的“后一帧复制就绪到结果回调返回”时间取 P85，包含转换、代理准备、算法执行与回调派发；另保存最近 30 项生成结果的实际显示/丢弃反馈。反馈只记一次，失败获取 drawable、过期、被更新原帧覆盖或 GPU 失败均记未显示，正数 presentedTime 回调记已显示。尺寸重建和原画面切换清空状态，上一代反馈不能写入新统计。

控制器在源帧到达时更新计划延迟。目标至少为一个源帧间隔加 1ms；按任务 P85 加提前提交余量（最多 20ms）及显示成功率余量选取。至少 12 项反馈后，显示率低于 80% 预留 6ms，80%～90% 预留 3ms，90% 以上预留 1ms；暖机用 2ms。增加最多 2ms/源帧，缩短最多 0.25ms/源帧。目标限制在两个源帧间隔或 100ms 的上限内（极慢输入时上限至少不低于一个源帧间隔加 1ms），避免通过无限排队掩盖处理跟不上。30fps 稳态目标范围约 34.3～66.7ms。它是计划时间，不是实际显示时延；系统仍可能晚于目标呈现。

单次慢任务不会直接支配 P85，窗口更新后可以恢复较短等待。Apple 忙时跳过的源帧对没有生成结果，因此不计作“中间帧显示失败”；显示率的分母是已经生成的任务，不能替代输出 fps 或证明稳定 2×。算法吞吐不足不能只靠增加时延解决。预测源间隔小于 25ms 时仍保留原并行路径，不启用提前排队调节。

工具栏在曲线下新增“自动调节 · 计划延迟 … · 中间帧显示 …”。计划延迟与上方实际测得的取帧→显示分开显示；旧库/屏幕来源没有 ADAPT 数据时隐藏该行。LOADED 标记 pipeline=adaptive-v4；ADAPT 每秒记录 elapsed、delayMs、processingBudgetMs 和 midpointDeliveryRate。

19 项自动测试通过：包括低负载缩短、高负载增加及上限、恢复限速、孤立尖峰抑制、相同耗时但不同显示成功率、非法输入/慢输入和重置。release 构建及签名通过。30fps、60fps、分辨率切换测试全部正常退出，最终日志无 ERROR，统计窗口内没有呈现序号倒序。

压力切换测试只对 GameHookFixture 的 --pressure-test 生效：第 4～8 秒额外延迟结果回调 15ms，用于可重复验证反馈响应，不是实际 GPU 压力基准，也不会影响鸣潮。计划延迟约 34ms → 峰值54ms → 34ms，压力期生成帧显示比例恢复到 100%，压力解除后逐步回落。整体输出窗口中位数约 60fps。普通 30fps 测试原帧 P50 的窗口中位数 49.65ms、输出 59.1fps；不是保证比前版更低，重点是随压力调整等待余量。普通 60fps 原并行路径约 41.36ms / 81.3fps，系统负载未锁定，不作为前后性能比较。

日志 latency-adaptive-{pressure,30,60,resize}.log，汇总 latency-adaptive-comparison.json；使用 12 秒 1080p 测试窗口，普通汇总丢弃前两个 METRICS 窗口，取其余窗口统计中位数，而非原始逐帧合并后的全程百分位。另使用独立应用副本检查实际工具栏状态，确认自动调节行布局、实时更新和退出测试；副本及其测试进程已关闭，现有鸣潮保留。新主程序和动态库已打包，用户需重新打开 SwitchViewer 并通过工具栏重新启动鸣潮，才能同时使用新库和新状态显示。
