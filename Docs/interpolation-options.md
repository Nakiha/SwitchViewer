# 插帧倍率与延迟容忍量

macOS 的采集处理、游戏插帧面板均可选择 **2× / 4× / 8×**，并独立保存配置。
倍率是用户选择的生成目标，设备过载时不会自动改成较低倍率。

勾选「限制插帧延迟」后，可输入 **0–250 ms**。它限制相对直接显示原始帧增加的
**主动缓冲等待**。默认不勾选，2× 沿用之前的时序策略；4×、8× 的默认缓冲最多
100 ms。0 ms 不给生成帧预留等待，直接保留原始帧，也跳过无用的插帧计算。

预算过小时，不能及时使用的插值帧会被丢弃。配置区显示生成帧未显示或超时状态，
实际显示帧率与 P95 时延仍在监控页查看。游戏设置下次启动生效；采集设置即时生效，
切换会清除旧的生成帧与呈现任务。录制期间禁止修改这两个配置。

**这不是操作到屏幕的硬性时延保证。** GPU 执行、呈现队列、屏幕刷新和上游采集
仍会增加等待；预算限制的是调度器主动添加的缓冲，不等于插帧算法耗时上限。
预算不足时保留用户的倍率和预算，丢弃不能使用的插值帧。

## 显示与设备限制

- 30 fps 输入选择 4× 时，目标为 120 fps；选择 8× 时，目标为 240 fps。
- 120 Hz 屏幕最多确认约 120 次呈现，无法显示全部 240 fps 输出。8× 仍会请求
  七个插值位置，但屏幕与呈现队列只能使用其中一部分。
- 增加预算可以改善帧的可用率，不能弥补持续不足的处理吞吐量。先降低倍率，或在
  游戏模式中选择 720p 处理偏好，再观察实际帧率和延迟。
- 本次未增加 iPad 的倍率设置；iPad 保留现有 2× 行为。

## 呈现实现

默认 2× 保留单输出完成回调、原始帧预提交、原有压力反馈与有限的原帧仲裁等待。
多倍及自定游戏预算使用独立的时间槽：每个位置有自己的目标时间和过期时间，
生成帧不会延长原始帧的提交时间。只允许一个 Apple 请求在途；过载不积压请求。

Apple 输出逐帧到达后按媒体时间调度，读取输出缓冲，不在请求完成前修改它。
4× 请求 0.25 / 0.5 / 0.75；8× 请求七个八分位置。配置参数使用相应的二分网格深度，
不是把输出帧数量直接传给配置。参见 [Apple 逐帧输出接口](https://developer.apple.com/documentation/videotoolbox/vtframeprocessor/processwithparameters:frameoutputhandler:?language=objc)。

游戏路径根据各位置就绪时间估计缓冲需求，再限制到用户预算；采集路径为各媒体时间
建立呈现槽并限制已有缓冲估计。两个路径均拒绝旧帧覆盖已经提交的新帧。
游戏录制使用实际插值位置保存媒体时间戳。多倍诊断记录帧角色与倍率，避免把偶数序号
的插值帧错误统计为原始帧。自定采集配置的延迟统计以原始帧为准。
